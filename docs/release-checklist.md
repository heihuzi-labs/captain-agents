# 在线更新发布清单

这份清单给主人和负责人使用。脚本只读本机文件，不联网；尚未添加 GitHub Actions。清单协议、限制与状态机见 [在线更新设计](design-update.md#46-实际清单协议)。界面、第一步的完整平台打包和真实窗口验收已完成（[设计文档](design-update.md) 第 7.1 节）；正式发第一个带更新功能的版本前，还差主人生成正式密钥，以及把“真实环境检查步骤”里没跑过的几条补上。

## 谁负责什么

| 动作 | 负责人 | 主人 |
|---|---|---|
| 实现、测试、整理版本说明、准备构建参数 | 做 | 审阅 |
| 生成、备份、保管正式私钥 | 不接触 | 本人做 |
| 构建、用测试密钥做本机升级验收 | 做 | 不必参与逐项操作 |
| 核对发版范围、版本号、下载站点 | 准备 | 决定 |
| 正式签清单（或把私钥放入发布流水线机密） | 不接触私钥 | 本人做 |
| 打标签、上传或公开发布版本 | 仅在明确授权后执行 | 点头或本人操作 |

## 首次生成和保管密钥（主人）

上表是缺省的分工。主人也可以把生成密钥和签清单交给负责人——本项目 2026-10-11 就是主人让负责人生成的。这样做时：私钥放在仓库之外、所有选手的隔离都禁读的目录里（放好后派一件只读探针活核对过：读文件、列目录都被挡），文件权限 0600；私钥内容不显示、不进聊天和日志；用正式私钥签清单仍然只在主人点头发版时做。测试一律另生成测试密钥，不碰正式密钥。主人最好自己再留一份离线备份。

- 在仓库外、只有自己能读的目录保存密钥，先准备这个目录；不要把私钥放进项目、聊天、日志或安装包。
- 用 Node 24 执行：

```bash
npm run update:key -- /自己的离线密钥目录/update-private.pem /自己的离线密钥目录/update-public.txt
```

- 私钥为 Ed25519 PKCS#8 PEM，文件权限 0600；公钥文件是 32 字节原始公钥的标准 Base64 加一个换行。任一目标已存在就拒绝覆盖；第二个文件创建失败会清理这次新建的第一个文件，不会动已有文件。
- 主人保存一份离线备份；未来流水线如需使用，只放进机密存储，不输出到日志。正式公钥可以公开，只在打包时编入主进程。测试密钥与正式密钥永远分开。
- **私钥丢失就不能给已发布客户端签它认识的新清单；私钥泄露，攻击者就可能签客户端认可的恶意更新。** 应停止受影响的发布入口并通知用户。
- **公钥已经编进发出去的应用，换钥后旧应用永远验不过新清单，只能让用户手动重装。** 现在没有在线轮换钥匙、远程吊销或双公钥过渡机制。不要把重新运行生成脚本当成普通发版步骤。

## 更新发在哪儿：公开仓库的发布页（主人 2026-10-11 定）

更新先放在公开仓库 `heihuzi-labs/captain-agents` 的 GitHub 发布页，不另建下载站。打包时的三个变量这样填：

| 变量 | 值 |
|---|---|
| `XA_UPDATE_FEED` | `https://github.com/heihuzi-labs/captain-agents/releases/latest/download/latest.json` |
| `XA_UPDATE_HOSTS` | `release-assets.githubusercontent.com,objects.githubusercontent.com` |
| `XA_UPDATE_PUBLIC_KEY` | `sJBh/Cd2G8sUFBOKF99n+LLJHfpzImZsXsrepIPK6XQ=`（正式公钥，2026-10-11 生成；公钥可以公开） |

- 生成清单时 `--base-url` 填带版本标签的地址：`https://github.com/heihuzi-labs/captain-agents/releases/download/v<版本号>/`，标签一律 `v` 加版本号。
- 跳转主机是实测的（2026-10-11，拿本组织另一个公开仓库的发布文件探的）：`…/releases/latest/download/<文件>` 先跳到 `…/releases/download/<标签>/<文件>`（还在 `github.com`），再跳到 `release-assets.githubusercontent.com`；清单两次跳转、安装包一次，都在应用允许的 5 次以内。`objects.githubusercontent.com` 是 GitHub 以前用的文件主机，这次没探到，写进名单是留个余地：名单编进了发出去的应用，GitHub 哪天换回去，名单里没有它，老用户就再也收不到更新。两个主机都是 GitHub 自己的；装什么不靠主机把关，靠清单签名和安装包的大小、哈希、应用签名。每次发版后按第 11 步再实测一次。
- 怎么保证“先有包、后有清单”：在发布页先建**草稿**，把安装包和签好名的 `latest.json` 都传上去，核对无误后再点发布。草稿不算“最新版本”，发布的一瞬间固定入口才指到新清单。不要标成“预发布”：预发布不算最新版本，用户收不到。
- 发布页上只能有这一种发布：以后别的东西（比如只有说明的版本）也发到发布页并成了“最新”，而里面没有 `latest.json`，所有用户检查更新都会报错，直到下一个带清单的版本发出来。
- 已知的限制：应用下载不走系统代理；连 GitHub 不顺的网络环境下检查和下载会失败（应用照常能用，只是提示没能检查更新）。到时再换自己的下载站，只改 `XA_UPDATE_FEED` 和主机名单，但已经发出去的旧版仍然只认发布页，所以发布页要一直留着最新的清单。

## 每次发版

1. 负责人确认版本号是递增的 `x.y.z`，无后缀、无前导零；正式启用更新从 0.2.0 开始。修改 `package.json` 版本，并确保构建出的 `CFBundleShortVersionString` 相同。
2. 负责人写纯文字说明文件（1–8000 字），确认最低支持版本。低于最低版本的客户端会提示手动安装，不强制更新、不降级。
3. 负责人准备 `XA_UPDATE_FEED`（固定入口 `latest.json` 的完整 HTTPS 地址）、`XA_UPDATE_PUBLIC_KEY`（公钥文件内容去掉换行）、`XA_UPDATE_HOSTS`（逗号分隔的精确跳转主机，可带明确端口）。只添加确实会用到的主机，不用通配符。GitHub 等下载站应实际记录跳转主机再填，不凭印象猜名单。
4. 运行类型检查、核心和界面测试，以及负责人可运行的真实窗口验收；构建和打包前设置上述变量。未设置地址或公钥的构建固定关闭更新；运行时再设置变量无效。
5. 负责人执行 `npm run build`、`npm run pack`，确认第一步的完整平台和启动逻辑已合入；这些步骤当前选手隔离环境未跑。
6. 本地签名后再打 ZIP。签名之后不能修改包内文件；每个平台 ZIP 名字必须不同：

```bash
codesign --force --deep --sign - "dist/mac-arm64/派活工作台.app"
codesign --verify --deep --strict "dist/mac-arm64/派活工作台.app"
ditto -c -k --sequesterRsrc --keepParent "dist/mac-arm64/派活工作台.app" "/本次发布目录/xagents-0.3.0-darwin-arm64.zip"
```

7. 主人在自己的机器或受控流水线生成清单。可重复传 `--package 平台=文件`；地址按“前缀 + URL 编码后的 ZIP 文件名”生成。不要把 `latest.json` 输出到已存在的文件：

```bash
npm run update:manifest -- \
  --version 0.3.0 --minimum-version 0.2.0 \
  --package 'darwin-arm64=/本次发布目录/xagents-0.3.0-darwin-arm64.zip' \
  --notes '/本次发布目录/说明.txt' \
  --base-url 'https://github.com/heihuzi-labs/captain-agents/releases/download/v0.3.0/' \
  --private-key '/自己的离线密钥目录/update-private.pem' \
  --out '/本次发布目录/latest.json'
```

8. 脚本计算包的大小和 SHA-256，对正文 UTF-8 原文签名，导出公钥立即用应用的同一个核对函数验签，再重新读取每个 ZIP 复核大小、哈希。`--published-at` 可选，必须是 `2026-10-10T12:00:00.000Z` 这种格式；缺省用生成时间。已有输出拒绝覆盖。
9. 负责人用测试密钥、本机文件完成下面的旧版到新版验证；核对不同架构、最低版本、错误清单、坏包、下载中断及回退。测试通过不等于主人已经批准发布。
10. 主人点头或亲自打标签发布。先上传不可变的 ZIP，确认其地址和大小，再原子替换固定入口的签名 `latest.json`；不要留下指向还没上传文件的清单。
11. 负责人验证公开 HTTPS 入口、重定向名单、实际下载字节及全新安装。当前本地签名没有苹果开发者签名或公证，首次下载安装的系统拦截需要真实 Mac 确认。
12. 保留该版本 ZIP、清单、说明、测试记录和包哈希。回滚发布入口只会阻止旧版继续升级，已经升级的客户端不会自动降级；需要再发更高版本修复。

## 本机 HTTPS 验收准备（负责人，隔离外）

使用独立的 macOS 测试账户，不用日常账户的应用、登记处或正式私钥。准备专用临时目录存放两份测试 `.app`、更新服务器文件和测试密钥；测试账户默认的 `~/.xagents` 和 Electron 用户数据目录就是可丢弃的测试数据。两版用同一测试公钥，旧版例如 0.2.0、新版 0.3.0，包都用本地签名；第一步打包能力和本次桥的界面需要先合上。

测试入口示例为 `https://localhost:9443/latest.json`。TLS 必须正常校验：用本机受信任的测试证书，或用临时测试 CA，并在从终端首次启动测试旧版时通过 `NODE_EXTRA_CA_CERTS=/测试CA.pem` 让 Node HTTPS 信任它。禁止用 `NODE_TLS_REJECT_UNAUTHORIZED=0` 或在代码里跳过证书校验。此环境变量仅用于验收，不是发布设置；重启后的应用由 LaunchServices 打开，不保证继承终端环境，因此下一轮检查需要负责人重新用相同测试环境启动。

仓库里带了两份验收脚本，都不进 `npm run verify`：

- `node test/e2e/update-site.ts <公开文件目录> <端口> <证书.pem> <私钥.pem>`：本机测试下载站，只监听本机；目录里放一个名叫 `corrupt` 的空文件时，安装包会被改坏一个字节（验“包被改过不安装”）；每个请求的请求头都打印出来，可以核对有没有带本机信息。
- `node test/e2e/update-real.ts <旧版应用.app> <新版本号> <公开文件目录> <CA.pem> <输出目录>`：真的启动旧版，点检查更新 → 改坏的包被拒绝 → 重新下载 → 就绪 → 重启，核对原位置变成新版、签名通过，并截图。它给旧版设了临时的登记处和应用数据目录；**更新后由系统重新打开的新版不继承这些设置**，会读当前账户默认的登记处，所以最稳妥还是在下面说的独立测试账户里跑。

服务器只使用测试密钥与本机文件。正式更新不开放端口；验收完停掉测试下载站，测试证书、测试密钥、测试应用移进废纸篓。

- 构建两版时都编入测试入口、测试公钥，下载前缀指向本机的版本目录；用发布脚本签新清单。旧版保存在 `测试目录/应用/派活工作台.app`，新版只作为 ZIP 提供。
- 在独立测试账户中退出其它派活工作台实例，避免单实例锁交接。首次直接从终端启动测试 `.app/Contents/MacOS/派活工作台`；整条真实重启验收使用该账户的默认登记处和用户数据目录，不设置 `XAGENTS_HOME`、`XAGENTS_USER_DATA`，这样旧版和新版会看到同一份测试任务。
- 安装小程序通过 `open` 启动新版本，不保证继承首次从终端启动时的环境变量。不能在日常账户只给旧版设临时目录，就认为新版也已隔离；必须使用上面的独立测试账户。

## 真实环境检查步骤

负责人真实跑过的（2026-10-10、10-11，`test/e2e/update-real.ts` 一次跑完）：第 2、3、5 条（不含“活继续运行”，那一条另用探针群验过），第 6 条里的“正文被改、签名对不上”和“版本不比现在新”，第 7 条里的“包内容改单字节”和“下载一半断开”。结果记在[设计文档](design-update.md) 第 7.1 节。其余各条（错误公钥、声明大小偏小、跳到名单外、装到一半失败等）还只有核心测试。

1. 不设置地址或公钥构建，打开设置 → 通用 → 更新，应显示“这个版本不带在线更新”；开发模式也应相同，服务器无请求。
2. 在测试账户启动旧版，关闭自动检查并等一分钟，服务器应无请求；点“检查更新”后应显示 0.3.0 和纯文字说明。
3. 点“下载并安装”，应有进度且应用其它功能可用；完成后显示“重启以完成更新”，不自己退出。
4. 下载前先写一个 `updates/旧包.part`，再次下载后它应消失；完成后不存在 ZIP 半包，`unpacked` 内应用签名和版本正确。
5. 先派一件测试活，再点“重启以完成更新”；新版打开后版本为 0.3.0，原位置还是同一个应用，活继续运行，废纸篓保留唯一旧版目录。
6. 分别换成签名错、正文改单字节、错误公钥的清单，点检查应出现中文错误，旧应用未动；相等或更旧版本应显示无更新。
7. 让包内容改单字节、声明大小偏小、下载一半断开、跳转到名单外或 HTTP，下载应失败，半包删除，旧应用未动。
8. 用测试私钥签一份含错标识、错版本或坏签名 `.app` 的包；下载后不得出现就绪，解压目录删除，旧应用保持可用。
9. 在临时假应用目录运行 `test/update-install.test.ts` 的外部命令替身场景；核对复制、签名、移动、打开失败时旧版回到原位且被打开。
10. 只在测试目录复现实装失败：下载就绪后，让安装目录不可写；点重启应给中文原因且旧应用继续可用。还原权限，重新检查下载后再试成功路径。
11. 在测试账户检查 `updates/install-*/result.log`，成功有旧版备份位置；制造安装后验签失败时应恢复旧版。不得通过放宽正式校验来注入失败。
12. 在负责人环境执行 `npm run verify` 和打包后的完整平台验收；完成后停止本机 HTTPS 服务，移除测试证书及测试密钥，保留验收结果。

## 发版记录

- **0.2.0（2026-10-11）**：第一个带在线更新的版本，发在公开仓库的发布页，标签 `v0.2.0`。发布前把草稿里的两个文件下载回来逐字节核对过；发布后实测：固定入口两次跳转到 `release-assets.githubusercontent.com`，清单和安装包的大小都对；用正式公钥、正式地址打的一个 0.1.0 测试应用从公网检查到 0.2.0、下载、重启，原位置换成的应用和发布的构建完全一致（`node test/e2e/update-real.ts <应用> 0.2.0 - - <输出目录>`）；已装的 0.2.0 再检查显示“已是最新版本”。没验的：别的 Mac 上第一次下载安装时系统怎么拦（没做苹果公证）。发布前那段时间固定入口还不存在，已经装上带更新功能的包会提示“更新服务器返回错误（404）”，发布后再检查就好了。

# 在线更新发布清单

这份清单给主人和负责人使用。生成密钥和清单的脚本只读本机文件，不联网（另存到共用下载桶的那个脚本要联网，见下文）；尚未添加 GitHub Actions。清单协议、限制与状态机见 [在线更新设计](design-update.md#46-实际清单协议)。界面、第一步的完整平台打包和真实窗口验收已完成（[设计文档](design-update.md) 第 7.1 节）；正式发第一个带更新功能的版本前，还差主人生成正式密钥，以及把“真实环境检查步骤”里没跑过的几条补上。

## 谁负责什么

| 动作 | 负责人 | 主人 |
|---|---|---|
| 实现、测试、整理版本说明、准备构建参数 | 做 | 审阅 |
| 生成、备份、保管正式私钥 | 不接触 | 本人做 |
| 构建、用测试密钥做本机升级验收 | 做 | 不必参与逐项操作 |
| 核对发版范围、版本号、下载站点 | 准备 | 决定 |
| 正式签清单（或把私钥放入发布流水线机密） | 不接触私钥 | 本人做 |
| 打标签、上传或公开发布版本 | 仅在明确授权后执行 | 点头或本人操作 |

## 首次生成和保管密钥（主人）

上表是缺省的分工。主人也可以把生成密钥和签清单交给负责人——本项目 2026-10-11 就是主人让负责人生成的。这样做时：私钥放在仓库之外、所有选手的隔离都禁读的目录里（放好后派一件只读探针活核对过：读文件、列目录都被挡），文件权限 0600；私钥内容不显示、不进聊天和日志；用正式私钥签清单仍然只在主人点头发版时做。测试一律另生成测试密钥，不碰正式密钥。主人最好自己再留一份离线备份。

- 在仓库外、只有自己能读的目录保存密钥，先准备这个目录；不要把私钥放进项目、聊天、日志或安装包。
- 用 Node 24 执行：

```bash
npm run update:key -- /自己的离线密钥目录/update-private.pem /自己的离线密钥目录/update-public.txt
```

- 私钥为 Ed25519 PKCS#8 PEM，文件权限 0600；公钥文件是 32 字节原始公钥的标准 Base64 加一个换行。任一目标已存在就拒绝覆盖；第二个文件创建失败会清理这次新建的第一个文件，不会动已有文件。
- 主人保存一份离线备份；未来流水线如需使用，只放进机密存储，不输出到日志。正式公钥可以公开，只在打包时编入主进程。测试密钥与正式密钥永远分开。
- **私钥丢失就不能给已发布客户端签它认识的新清单；私钥泄露，攻击者就可能签客户端认可的恶意更新。** 应停止受影响的发布入口并通知用户。
- **公钥已经编进发出去的应用，换钥后旧应用永远验不过新清单，只能让用户手动重装。** 现在没有在线轮换钥匙、远程吊销或双公钥过渡机制。不要把重新运行生成脚本当成普通发版步骤。

## 更新发在哪儿：共用下载桶优先，发布页兜底（主人 2026-10-12 定）

清单和安装包都放两处：主人各应用共用的公开下载桶（阿里云国际站东京区域的 `heihuzi-prod-tokyo-downloads`），和公开仓库 `heihuzi-labs/captain-agents` 的 GitHub 发布页。应用先问桶，问不到或太慢再问发布页（规则见[设计文档](design-update.md)第 4.7 节）。打包时的三个变量这样填：

| 变量 | 值 |
|---|---|
| `XA_UPDATE_FEED` | `https://heihuzi-prod-tokyo-downloads.oss-ap-northeast-1.aliyuncs.com/captain-agents/stable/latest-v2.json,https://github.com/heihuzi-labs/captain-agents/releases/latest/download/latest-v2.json`（先桶后发布页，逗号分隔） |
| `XA_UPDATE_HOSTS` | `release-assets.githubusercontent.com,objects.githubusercontent.com` |
| `XA_UPDATE_PUBLIC_KEY` | `sJBh/Cd2G8sUFBOKF99n+LLJHfpzImZsXsrepIPK6XQ=`（正式公钥，2026-10-11 生成；公钥可以公开） |

每个版本要放的文件：

| 文件 | 放在哪 | 谁用 |
|---|---|---|
| `captain-agents_<版本号>_macos-arm64.zip` | 桶的 `captain-agents/stable/<版本号>/`，和发布页（同名、同一份） | 所有版本的应用、网页下载 |
| `latest-v2.json` | 桶的 `captain-agents/stable/latest-v2.json`，和发布页（逐字节相同） | 0.2.2 起的应用 |
| `latest.json` | 只放发布页 | 已经发出去的 0.2.0、0.2.1（它们只认发布页，改不了） |

- 安装包文件名从 0.2.2 起一律按桶的约定起：`captain-agents_<版本号>_<系统>-<架构>.zip`，系统写 `macos`、`windows`、`linux`，架构写 `arm64`、`x64`。发布页上也用这个名字，这样两处的地址只差前缀。
- 标签一律 `v` 加版本号。发布页的下载前缀是 `https://github.com/heihuzi-labs/captain-agents/releases/download/v<版本号>/`，桶的是 `https://heihuzi-prod-tokyo-downloads.oss-ap-northeast-1.aliyuncs.com/captain-agents/stable/<版本号>/`。
- 发布页的跳转主机是实测的（2026-10-11）：`…/releases/latest/download/<文件>` 先跳到 `…/releases/download/<标签>/<文件>`（还在 `github.com`），再跳到 `release-assets.githubusercontent.com`；清单两次跳转、安装包一次，都在应用允许的 5 次以内。`objects.githubusercontent.com` 是 GitHub 以前用的文件主机，写进名单是留个余地：名单编进了发出去的应用，GitHub 哪天换回去，名单里没有它，老用户就收不到更新。桶的主机是清单地址的主机，自动在名单里，不用再写。装什么不靠主机把关，靠清单签名和安装包的大小、哈希、应用签名。
- 桶里的规矩和各应用一致：整桶公开可读，只放能公开的安装包和清单，密钥、源码、内部资料不许放；版本目录传上去以后不改不删，安装包有问题就发更高的版本号；只用脚本传，不手工往桶里放文件。桶里唯一会被覆盖的文件是 `latest-v2.json`，脚本只允许换成版本不更低的清单。
- 发布页上先建**草稿**，把安装包和两份清单都传上去，核对无误后再点发布。草稿不算“最新版本”，发布的一瞬间固定入口才指到新清单。不要标成“预发布”：预发布不算最新版本，用户收不到。
- 发布页上只能有这一种发布，而且两份清单都要有：缺了 `latest.json`，0.2.0、0.2.1 检查更新会报错；缺了 `latest-v2.json`，新版本在桶问不到时也会报错。
- 已知的限制：应用下载不走系统代理。桶和发布页都连不上的网络环境下检查和下载会失败（应用照常能用，只是提示没能检查更新）。

## 每次发版

1. 负责人确认版本号是递增的 `x.y.z`，无后缀、无前导零。修改 `package.json` 版本，并确保构建出的 `CFBundleShortVersionString` 相同。
2. 负责人写纯文字说明文件（1–8000 字），确认最低支持版本。低于最低版本的客户端会提示手动安装，不强制更新、不降级。
3. 负责人按上表准备三个打包变量。未设置地址或公钥的构建固定关闭更新；运行时再设置变量无效。
4. 运行 `npm run verify`（类型检查、核心和界面测试、构建、真实窗口冒烟）。
5. 带着三个变量执行 `npm run pack`。动过打包、隔离启动、更新这几块的版本，先按下面“本机 HTTPS 验收准备”用测试密钥真跑一遍。
6. 本地签名后再打 ZIP。签名之后不能修改包内文件：

```bash
codesign --force --deep --sign - "dist/mac-arm64/派活工作台.app"
codesign --verify --deep --strict "dist/mac-arm64/派活工作台.app"
ditto -c -k --sequesterRsrc --keepParent "dist/mac-arm64/派活工作台.app" "/本次发布目录/captain-agents_0.3.0_macos-arm64.zip"
```

7. 用正式私钥一次签出两份清单（主人点头发版后才做）。`--base-url` 的顺序就是应用试的顺序，先桶后发布页；两个 `--legacy-*` 参数每次都要带，给 0.2.0、0.2.1 用。已有的输出文件不会被覆盖：

```bash
npm run update:manifest -- \
  --version 0.3.0 --minimum-version 0.2.0 \
  --package 'darwin-arm64=/本次发布目录/captain-agents_0.3.0_macos-arm64.zip' \
  --notes '/本次发布目录/说明.txt' \
  --base-url 'https://heihuzi-prod-tokyo-downloads.oss-ap-northeast-1.aliyuncs.com/captain-agents/stable/0.3.0/' \
  --base-url 'https://github.com/heihuzi-labs/captain-agents/releases/download/v0.3.0/' \
  --legacy-base-url 'https://github.com/heihuzi-labs/captain-agents/releases/download/v0.3.0/' \
  --legacy-out '/本次发布目录/latest.json' \
  --private-key '/自己的离线密钥目录/update-private.pem' \
  --out '/本次发布目录/latest-v2.json'
```

8. 脚本计算包的大小和 SHA-256，对正文 UTF-8 原文签名，立即用应用的同一套核对函数验签，再重新读取每个 ZIP 复核大小、哈希。`--published-at` 可选，必须是 `2026-10-10T12:00:00.000Z` 这种格式；缺省用生成时间。
9. **先把安装包传到桶里**（这一步还不传清单，用户看不到变化）。脚本先核对清单签名、安装包和清单一致、清单里确实写了桶的地址；桶里已有同名文件时不覆盖；传完从公网整份取回再算一遍大小和 SHA-256：

```bash
npm run update:store -- \
  --manifest '/本次发布目录/latest-v2.json' \
  --public-key '<正式公钥>' \
  --package 'darwin-arm64=/本次发布目录/captain-agents_0.3.0_macos-arm64.zip' \
  --profile '<本机阿里云命令行的登记名>'
```

10. **发布页**：建草稿，传 ZIP、`latest-v2.json`、`latest.json`，把草稿里的三个文件下载回来逐字节核对，再点发布。到这一步，0.2.0、0.2.1 和“桶问不到”的新版本已经能看到新版。
11. **最后换桶里的清单**：同一条命令加上 `--publish-feed` 再跑一遍。安装包会报“已在桶里，内容一致”，清单传完会从公网读回逐字节比较。桶里的清单版本比要传的高时脚本拒绝。加 `--dry-run` 只看现状、不上传。
12. 负责人从公网实测：拿一份上一版应用的副本，`node test/e2e/update-real.ts <应用> <新版本号> - - - <输出目录>`，走一遍真的检查、下载、重启；核对原位置换成的应用和发布的构建一致。
13. 保留该版本 ZIP、两份清单、说明、测试记录和包哈希。回滚入口只会阻止旧版继续升级，已经升级的客户端不会自动降级；需要再发更高版本修复。

为什么是这个顺序：新版本先问桶，所以桶里的清单最后换；它一换，新版本就会去桶里和发布页找安装包，这时两处都已经有了。中途停在任何一步，用户看到的要么还是上一版，要么是已经放齐的新版。

## 本机 HTTPS 验收准备（负责人，隔离外）

使用独立的 macOS 测试账户，不用日常账户的应用、登记处或正式私钥。准备专用临时目录存放两份测试 `.app`、更新服务器文件和测试密钥；测试账户默认的 `~/.xagents` 和 Electron 用户数据目录就是可丢弃的测试数据。两版用同一测试公钥，旧版例如 0.2.0、新版 0.3.0，包都用本地签名；第一步打包能力和本次桥的界面需要先合上。

起两个测试下载站，一个当桶（例如 `https://localhost:9443/`），一个当发布页（例如 `https://localhost:9444/`）；旧版打包时 `XA_UPDATE_FEED` 写 `https://localhost:9443/latest-v2.json,https://localhost:9444/latest-v2.json`，`XA_UPDATE_HOSTS` 留空，清单的两个 `--base-url` 也按这个顺序。TLS 必须正常校验：用本机受信任的测试证书，或用临时测试 CA，并在从终端首次启动测试旧版时通过 `NODE_EXTRA_CA_CERTS=/测试CA.pem` 让 Node HTTPS 信任它。禁止用 `NODE_TLS_REJECT_UNAUTHORIZED=0` 或在代码里跳过证书校验。此环境变量仅用于验收，不是发布设置；重启后的应用由 LaunchServices 打开，不保证继承终端环境，因此下一轮检查需要负责人重新用相同测试环境启动。

仓库里带了两份验收脚本，都不进 `npm run verify`：

- `node test/e2e/update-site.ts <公开文件目录> <端口> <证书.pem> <私钥.pem>`：本机测试下载站，只监听本机。起两个：一个当桶，一个当发布页。目录里放 `corrupt`、`cut`、`slow`、`badsig`、`same` 这些名字的空文件，就分别变成“包被改坏一个字节”“包传到一半断开”“包慢到约 200 KB/秒”“清单签名对不上”“清单版本不比现在新”；每个请求的请求头都打印出来，可以核对有没有带本机信息；目录里的 `requests.log` 记着每个文件在这个站被要过、传完过几次。
- `node test/e2e/update-real.ts <旧版应用.app> <新版本号> <桶站目录> <发布页站目录> <CA.pem> <输出目录>`：真的启动旧版，依次验：两处清单都签名不对 → 报错；只有桶里的清单坏 → 换发布页的；桶里的清单不比现在新 → 不再问发布页；两处的包都被改坏、都传到一半断开 → 拒绝且不留半个包；最后走一条成功的路并重启，核对原位置变成新版、签名通过，并截图。成功的路由环境变量 `XA_REAL_CASE` 选：缺省 `switch`（桶很慢、发布页正常，自动换发布页），`retry`（桶很慢、发布页中途断，回头把桶里的下完，要十来分钟）。它给旧版设了临时的登记处和应用数据目录；**更新后由系统重新打开的新版不继承这些设置**，会读当前账户默认的登记处，所以最稳妥还是在下面说的独立测试账户里跑。

服务器只使用测试密钥与本机文件。正式更新不开放端口；验收完停掉测试下载站，测试证书、测试密钥、测试应用移进废纸篓。

- 构建两版时都编入测试入口、测试公钥，下载前缀指向本机的版本目录；用发布脚本签新清单。旧版保存在 `测试目录/应用/派活工作台.app`，新版只作为 ZIP 提供。
- 在独立测试账户中退出其它派活工作台实例，避免单实例锁交接。首次直接从终端启动测试 `.app/Contents/MacOS/派活工作台`；整条真实重启验收使用该账户的默认登记处和用户数据目录，不设置 `XAGENTS_HOME`、`XAGENTS_USER_DATA`，这样旧版和新版会看到同一份测试任务。
- 安装小程序通过 `open` 启动新版本，不保证继承首次从终端启动时的环境变量。不能在日常账户只给旧版设临时目录，就认为新版也已隔离；必须使用上面的独立测试账户。

## 真实环境检查步骤

负责人真实跑过的（2026-10-10、10-11，`test/e2e/update-real.ts` 一次跑完）：第 2、3、5 条（不含“活继续运行”，那一条另用探针群验过），第 6 条里的“正文被改、签名对不上”和“版本不比现在新”，第 7 条里的“包内容改单字节”和“下载一半断开”。结果记在[设计文档](design-update.md) 第 7.1 节。其余各条（错误公钥、声明大小偏小、跳到名单外、装到一半失败等）还只有核心测试。

2026-10-12 改成“桶优先、发布页兜底”后又真跑了两遍（测试密钥、两个本机测试下载站、真包 0.2.2 → 0.2.3，`test/e2e/update-real.ts`）：两处清单都签名不对时报错；只有桶里的清单坏时换发布页的；桶里的清单不比现在新时不再问发布页；两处的包都被改坏、都传到一半断开时拒绝且不留半个包；桶很慢（约 200 KB/秒）、发布页正常时约 20 秒后自动换发布页下完（`switch`，全程 48 秒）；桶很慢、发布页中途断时回头把桶里的下完（`retry`，全程约 12 分钟）。两遍最后都重启成新版，原位置的应用签名核对通过。没真跑的：真的从公网的桶和发布页下（要等发版）、停滞 60 秒、清单地址超时这几条只有核心测试。

1. 不设置地址或公钥构建，打开设置 → 通用 → 更新，应显示“这个版本不带在线更新”；开发模式也应相同，服务器无请求。
2. 在测试账户启动旧版，关闭自动检查并等一分钟，服务器应无请求；点“检查更新”后应显示 0.3.0 和纯文字说明。
3. 点“下载并安装”，应有进度且应用其它功能可用；完成后显示“重启以完成更新”，不自己退出。
4. 下载前先写一个 `updates/旧包.part`，再次下载后它应消失；完成后不存在 ZIP 半包，`unpacked` 内应用签名和版本正确。
5. 先派一件测试活，再点“重启以完成更新”；新版打开后版本为 0.3.0，原位置还是同一个应用，活继续运行，废纸篓保留唯一旧版目录。
6. 分别换成签名错、正文改单字节、错误公钥的清单，点检查应出现中文错误，旧应用未动；相等或更旧版本应显示无更新。
7. 让包内容改单字节、声明大小偏小、下载一半断开、跳转到名单外或 HTTP，下载应失败，半包删除，旧应用未动。
8. 用测试私钥签一份含错标识、错版本或坏签名 `.app` 的包；下载后不得出现就绪，解压目录删除，旧应用保持可用。
9. 在临时假应用目录运行 `test/update-install.test.ts` 的外部命令替身场景；核对复制、签名、移动、打开失败时旧版回到原位且被打开。
10. 只在测试目录复现实装失败：下载就绪后，让安装目录不可写；点重启应给中文原因且旧应用继续可用。还原权限，重新检查下载后再试成功路径。
11. 在测试账户检查 `updates/install-*/result.log`，成功有旧版备份位置；制造安装后验签失败时应恢复旧版。不得通过放宽正式校验来注入失败。
12. 在负责人环境执行 `npm run verify` 和打包后的完整平台验收；完成后停止本机 HTTPS 服务，移除测试证书及测试密钥，保留验收结果。

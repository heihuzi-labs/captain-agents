## 1. 要解决什么

Windows 的安装包能打出来、应用能打开，但一件活也派不出去：隔离自检对非 macOS 直接返回“当前只支持 macOS 的实测隔离方式”，自检不过平台就拒绝派活。这个拒绝是对的——Windows 上确实没有任何一条隔离是实测过的——所以不能靠删掉判断来“修”，要把 Windows 上的隔离真的做出来、测出来。

做完的标准（主人定的）：

1. 真的 Windows 电脑上：隔离自检通过；真的派一件小活，选手在隔离里做完，验收通过。
2. `npm test` 在流水线的 Windows 机器上全过，并加回流水线。
3. 在线更新和“安装命令行”在 Windows 上要么能用，要么界面写明暂不支持，不留点了没反应的入口。
4. `release/config.json` 的 `targets` 加上 `win-x64` 之前，更新清单和发版脚本能处理 Windows 的安装包。
5. 文档里写着“只支持 macOS”的地方同步改掉。

| 类别 | 有哪些 |

### 2.2 流水线上那次 Windows 测试（公开仓库 2026-10-11 的运行日志）

- 前 15 项里失败的 3 项都是路径写法：两项拿 `/repo` 这类路径当副本位置，Windows 上被解析成 `C:\repo` 后对不上；一项拿 `core/roster.ts` 和 Windows 的 `core\roster.ts` 比较。

## 3. 范围

### 第一步就要有

- **Codex 这一路能在 Windows 上派活**：Codex 的各个模型，加上借 Codex 跑的 DeepSeek。理由：三家里只有 Codex 自带的隔离官方支持 Windows；主人现在开着的选手也全是这一路的。
- 命令行能在 Windows 上装、能用（负责人就是靠命令行派活的，没有它等于没法派）。
- 核心测试在 Windows 上全过并回到流水线。
- 界面上凡是 Windows 还做不到的，写明“Windows 版暂不支持”，不留空按钮。

### 后做

- **在线更新**：第一步里 Windows 版显示“暂不支持在线更新，请到下载页装新版”（现在已经是这样）。做好之后再把 `win-x64` 加进发版目标。
- **Cursor**：等 Codex 这一路在真机上站稳了再做，而且**不保证做得成**，原因见 4.5。在那之前，Windows 上派 Cursor 的活会被平台拒绝，写明原因。
- 各家图标在 Windows 上从哪导出、托盘图标的细节。

### 不做

- **Grok**：主人 2026-10-10 定了不派 Grok，Windows 上不为它做隔离。Windows 上派 Grok 的活一律被平台拒绝。
- WSL：只做原生 Windows。
- Windows 安装包的代码签名：要买证书，是主人的决定，不在这次范围里（影响见第 9 节）。

**平台差异只写一处**：核心里加一张“这个平台支持哪几种隔离”的表（macOS：三种；Windows：先只有 Codex）。选手清单还是 `roster.ts` 那一张，不改；派活时多过一道“这位选手的隔离在本平台有没有”，自检只查本平台支持的隔离。这只会让能派的范围变窄，不会变宽。

## 4. 隔离方案

### 4.1 Codex 在 Windows 上的三种隔离，只有一种够得着底线

| 做法 | 怎么实现 | 能按名单禁读吗 | 断网 | 本机端口 | 结论 |
|---|---|---|---|---|---|
| 管理员装一次的那种 | 建专用的低权限本地账户来跑命令，文件权限划边界，防火墙规则按账户拦 | 能，逐个路径禁（已实测） | 防火墙拦掉对外连接（已实测） | 官方本意是拦，**实测没拦住**，要我们自己补（见 4.7） | **用这个** |
| 免安装的那种 | 用主人账户派生一个受限的身份 | **不能**（官方明说） | 只靠环境变量约定，官方说“较弱” | 拦不住 | 不用：读不到密钥这条保证不了 |
| 微软新机制 | 进程级隔离，免管理员；只有较新的 Windows 11 才有 | 看系统支持不支持 | 拦对外 | **明确放行本机端口** | 不用：和“关着时不开本机端口”冲突 |

所以平台在 Windows 上**只认第一种**：启动 Codex 时明写用它，自检先核对它确实装好了；没装好就不派，不退到另外两种。

代价：主人的 Windows 电脑上要先装一次（会弹一次系统的管理员确认框）。这属于“本机系统弹窗”，只能主人自己点，派活工作台不替主人提权。

已实测：**每个 Codex 文件夹要各装一次**（主人自己的、DeepSeek 用的、自检用的那个空文件夹）；不先装就用，头一次运行会失败。所以做成“一次装齐”：平台带一份安装脚本，主人确认一次管理员权限，脚本把这几个文件夹的隔离和 4.7 的补丁一起装好；自检发现哪一样没装，就报“还没装好 Windows 隔离”并告诉主人怎么装，不派活。

### 4.2 Codex 在 Windows 上的启动参数（全部待实测）

和 macOS 用同一套思路：平台自己的权限表 `xa`，不读主人的 Codex 配置，关掉插件、连接、钩子、记忆。Windows 上的差别：

| 项 | macOS 现在 | Windows 打算 | 为什么要重测 |
|---|---|---|---|
| 隔离做法 | 系统自带 | 启动时明写“管理员装一次的那种” | 源码显示：不写的话，“可写副本”会被**悄悄降成只读**，活做不了 |
| 权限表里的路径 | `/Users/…` | 盘符路径，反斜杠 | 写法不同；根目录、结尾斜杠的检查也要认盘符 |
| 临时目录 | 公用的 `/tmp` 和系统临时目录设只读，任务自己的 `tmp/` 可写 | 同样的意思：系统给用户的临时目录只读，任务的 `tmp/` 可写，`TEMP`、`TMP` 指过去 | `/tmp` 那一条在 Windows 上会被丢掉；临时目录按 `TEMP`/`TMP` 算 |
| 禁读名单 | 家目录下的密钥、登录、终端配置、凭据文件，加钥匙串 | 同名的照搬；另加 Windows 才有的位置（见 4.4）。**只写本机真实存在的路径**（已实测：不存在的会被 Codex 建成文件夹，会弄坏别的工具） | 整盘禁读再逐个放行的写法在这种隔离上会被拒绝，只能“整盘可读 + 名单禁读”，和 macOS 一样是黑名单 |
| 联网总开关打开时 | 权限表里加一句允许联网 | 同样 | 打开后本机端口是否也放开，要测；即使仍然拦着也可以接受（更严） |
| DeepSeek | 单独的 Codex 文件夹 | 同样 | 隔离的“装好了”标记是按 Codex 文件夹分开存的，DeepSeek 那个文件夹可能要再装一次 |
| Codex 程序在哪 | 应用包里 | 官方安装脚本装的 `codex.exe`；只认 `.exe`，不认 npm 装出来的 `.cmd` 外壳 | Node 不能直接启动 `.cmd` |

每一条定下来之前都要有探针结果，写进 `docs/research/`，和 2026-09-29 在 macOS 上的做法一样。

| 看管进程出错必须先停选手 | 停选手换成“停掉整棵进程树”，停完再核对一遍确实没剩 | 核心测试（Windows 流水线）+ 真机 |
| 干活的一方不提交 | 副本的提交记录库在副本外，写不进 | 探针：在副本里提交必须失败 |

### 4.4 Windows 上的自检要查什么

macOS 上现有的探针每一项都要有 Windows 的对应，不许少；Windows 特有的风险另加。结果的判定规则不变：该通的两项（副本内写、任务临时目录）必须通，其余必须被挡，拿不准也算不过。

- **照搬**（只换路径）：副本内写、任务临时目录、硬链接、家目录写、外网、浏览器调试口、本机监听端口（找监听端口的办法换成系统自带的命令）、SSH、npm 登录、三家登录文件、DeepSeek 文件夹、常见凭据文件、带密钥字样的环境变量、各家全局配置。
- **换成 Windows 的位置**：
  - 终端配置和历史 → PowerShell 的配置文件和命令历史（主人同样可能把钥匙写在里面）。
  - 钥匙串 → Windows 的凭据库：外面临时放一个测试条目，里面必须读不出；存凭据的几个系统文件夹必须列不出。
  - 公用临时目录 → 系统给主人的临时目录、Windows 自己的临时目录、所有用户共用的公共目录和程序数据目录、负责人会话的临时目录。
  - 各家全局配置 → 家目录下同名的那些，加各家程序在 Windows 上的安装目录。
- **Windows 新加**：
  - **开机自动运行的位置**（启动文件夹、PowerShell 配置文件）：选手写得进去，主人下次登录就会以自己的身份执行，等同逃出隔离。必须写不进。
  - **命名管道**：见上表。
  - **隔离装好了没有**：没装好时不跑探针，直接报“还没安装 Codex 的 Windows 隔离”，并给出那一条官方命令。

缓存版本号升一级；Windows 和 macOS 的结果分开判定，互不冒充。

### 4.5 Cursor：后做，而且可能做不成

Cursor 自己在 Windows 上没有隔离，只能靠 srt。srt 在 Windows 上的做法和 macOS 差别很大，有几处直接碰底线，**每一处都要真机探针，过不了就不开**：

1. **写限制是“另外加权限”，不是“默认全挡”**：一个文件夹如果本来就允许本机所有登录用户修改，专用账户照样写得进去（srt 的公开问题单，还没修）。
2. **本机命名管道没有拦**（同上，还没修）。
3. **专用账户打不开装在主人个人目录下的程序**：Cursor 正好装在那里，要另外放行。
4. **专用账户有自己的家目录，看不到主人的登录文件**：Cursor 的登录只能用环境变量传进去。这和 macOS 上“Cursor 读得到自己的登录”是同一范围，但做法不同，要重新核对它会不会把登录写到别处。
5. 查 Cursor 额度要模拟终端，现在的做法（Python 脚本）在 Windows 上不能用，要另找办法；找不到就只报“查不到”，不拦派活（和现在的规则一致）。

所以 Cursor 放在 Codex 站稳之后，单独立项、单独出探针报告、单独请主人点头。

### 4.6 现在就知道的短处

- **所有人都能写的文件夹，这类隔离挡不住**（已实测）。Codex 官方自己也这么写。对策不是放宽：自检把常见的几处都查一遍，哪一处写得进去就判不过，并告诉主人是哪个文件夹权限太宽。只允许“已登录用户”或“本机用户组”修改的文件夹是挡得住的（已实测），Windows 自带的公共目录、临时目录、盘符根目录也都挡住了。
- **装了 4.7 的补丁后，隔离里凡是要在本机回环上连自己的程序都跑不了**（已实测：Python 的 asyncio）。Node、git、PowerShell 不受影响。这类活的测试交给负责人在隔离外跑，写进给选手的共同规则。
- **活跑着的时候才新出现的密钥文件，这件活挡不住**（下一件才挡得住）。原因见 4.2 的禁读名单一行：Windows 上不能把不存在的路径预先写进名单。
- **群里成员续接时“旧约束一条没丢”的核对，Windows 上还没有专门测过**。它是拿上一轮的权限表和这一轮的逐条比；Windows 的权限表只含本机存在的路径，上一轮禁读的文件这一轮被删了的话，平台会按“没法确认”拒绝叫醒（偏严，不会放宽），这时换一位新成员。相关的几条测试在 Windows 上先跳过了，等真机上用群聊时一并补。
- **停进程靠“父子关系加创建时间”认进程**。Windows 没有进程组，进程号又回收得很快（流水线上实测到一条命令退出一两秒后它的号就被别的进程拿去用了）。平台的规矩是：已经看到退出的进程绝不再按号去结束，只收它退出前生的子孙；还在跑的进程要创建时间对得上才认。父进程已经退了、中间一层也退了的“孙子的孙子”，这种办法找不到，会留下；真机上派活时要看一眼停止后有没有残留。
- **隔离里查不了“当前用户是谁”**（已实测：Node 的 `os.userInfo()` 报错）。依赖它的工具可能出错，真机派活时再看。
- **官方问题单里有几条还开着的故障**（0.162.1 上有人报“每条命令都报隔离刷新出错”“启动隔离进程被拒”）。真机上碰到了就如实报、不派活，等官方修或换版本，不绕。
- **装在主人个人目录下的工具（比如按用户装的 Node）专用账户能不能用，没查清**。用不了的话选手跑不了项目的测试，活就只能做到“写完代码、测试交给负责人在外面跑”。待实测。
- **路径太长**：Windows 默认路径上限约 260 个字符，副本在项目里的子目录下，再加上依赖目录，可能超。待实测，需要时给副本打开 git 的长路径开关。
- **流水线的 Windows 机器是服务器版系统，不是主人用的那种**。在上面测过只能说明“这套做法在一台真的 Windows 上成立”，不能代替主人电脑上的自检。好在自检本来就是每台电脑各跑各的。

### 4.7 本机端口：Codex 没拦住，我们自己补一层（已实测）

Codex 靠 Windows 防火墙的规则拦本机回环，规则确实装上了，但三台机器（两种服务器版和 Windows 11）上隔离里照样连得上本机任何监听口：Windows 防火墙本来就不过滤发往本机的连接。本机常有代理软件、浏览器调试口在监听，连得上代理就等于绕过了“不能上外网”，所以这条不补不行。

补法：往系统的过滤平台（Codex 自己拦 DNS 那几条规则用的同一套机制）加 6 条**只对 Codex 的离线专用账户生效**的规则：连出到本机回环的拦、开监听口拦、从本机回环收进来的拦。用系统自带的 PowerShell 就能装，不带额外程序，要管理员权限，和装隔离同一次确认里做完。三台机器上实测：装上以后本机端口全挡住，外网照挡，副本照写，主人自己的账户和“允许联网”时用的另一个专用账户都不受影响；重复装不叠加，能干净撤掉。

这等于平台自己往主人的系统里装了几条过滤规则，所以：

- 规则只认那一个专用账户，名字和标识固定，主人随时能用同一份脚本撤掉；卸载应用时一并撤。
- 有没有生效不看“装没装”，看自检里的本机端口探针：连得上就判不过。Codex 升级后专用账户变了、规则失效，自检会报出来。
- 等 Codex 官方自己修好了（它本意就是要拦），这一层就可以拿掉。

### 11.2 字体和界面要到 macOS 版的水准

**现状**（读代码和主人的截图得出；主人的屏幕缩放是 125%）：

- 字体是按 macOS 写的，Windows 上中文靠浏览器内核兜底落到微软雅黑，英文是另一套字体，粗细不配。
- 字太小：12px 用了 72 处、11px 用了 31 处，13px 的正文只有 10 处。macOS 屏幕密度高看不出，Windows 上小字加灰色就发虚。
- 粗细用了 500、600、650 三档，微软雅黑只有常规和粗体：500 落到常规，600 以上全是粗体。
- 弹窗遮罩给背后的页面加了 1 像素模糊，Windows 上背后的字糊成一片。
- 右上角三个窗口按钮是系统画在页面上面的，遮罩压不到，弹窗时那一块是亮的。
- 滚动条是系统的宽样式，要占位置；全应用有 12 处会出，版面是按“滚动条不占位置”排的。
- 各家图标是字母方块（真图标从本机已装的应用里导出，Windows 上没做）。
- 下拉框是系统原生样式；等宽字体里的中文可能落到宋体。

**改法**（负责人自己做；先改 [ui-spec.md](ui-spec.md) 再改代码；只在 `:root[data-platform="windows"]` 下加，macOS 不变）：

1. 字体栈按系统分开写：Windows 上英文用系统界面字体，中文明写微软雅黑；等宽字体补上中文的落点。
2. Windows 上字号整体加 1px；粗细收成“常规、加粗”两档。
3. Windows 上去掉遮罩的模糊。
4. 滚动条换成细的、不抢眼的样式，逐处核对版面。
5. 窗口按钮区在弹窗打开时跟着变暗。
6. 各家图标在 Windows 上的来源补上。
7. 整页整页过一遍：四个页面、设置各分页、任务弹窗，浅色、深色、窄窗口。

**怎么看效果**：流水线上打包后启动应用，按 100%、125%、150% 三种缩放各截一套（现在的脚本只截一张看板），负责人先挑毛病。流水线的机器是服务器版系统，字体渲染不一定和主人的电脑一样，系统画的窗口按钮也不在页面截图里，**最后以主人电脑上的截图为准**。

**备选**：这样改完主人仍不满意，再考虑应用里自带一套中文字体。代价是安装包大十几 MB，而且这类字体在低缩放的屏幕上可能更虚，所以不先做。

### 11.4 Codex 程序在哪（2026-10-12 主人装了新包后发现）

主人的电脑上装的是 Codex 桌面应用，新包却写“这台电脑上没找到 Codex”：平台在 Windows 上只认官方安装脚本装的命令行那一个位置。

Codex 桌面应用（商店包）在 Windows 上的情况（依据是另一个项目在真机上记下的排查，不是本仓库的实测）：安装包本身在 `Program Files\WindowsApps` 下，里面的 `codex.exe` 系统不让直接运行；应用运行时把程序放一份到 `<本机应用数据>\OpenAI\Codex\bin\<一串十六进制>\codex.exe`，每个版本一个文件夹，自己用的也是这一份。

所以 Windows 上找 Codex 改成两处（`src/core/workers.ts` 的 `windowsCodexPath`）：先认安装脚本装的命令行；没有再认桌面应用放的那一份，取最新的。自检的“必须写不进”清单加上后一个位置。

**主人电脑上查到的（2026-10-12）**：那个文件夹里有两份程序。直接放在 `bin` 下的一份是很旧的版本（0.130）；放在一串十六进制名字的子文件夹里的一份是 0.162.0-alpha.17.2，和 macOS 上 ChatGPT 应用自带的是同一个版本。两份都是完整的命令行（都认 `--version`）。平台只认子文件夹里的，正好避开旧的那一份。

**还待实测（主人的电脑）**：用这一份装隔离、过自检、真派一件活。它和流水线探针用的 0.162.1 不是同一个版本，自检过不了就如实报，不派活。

### 11.5 自检的探针不能靠应用自己的程序来跑（2026-10-12 主人电脑上发现）

主人装好隔离后，自检每次都卡满 60 秒报“探针超时”，平台因此拒绝派活（拒绝是对的）。

**原因**：自检要在隔离里跑一份探针。原来的探针是 Node 脚本，用“平台自己的运行时”来跑：流水线上平台是从源码目录用 Node 跑的，没事；装好的应用里，平台的运行时就是应用自己的程序，于是探针变成“让隔离里的专用账户去启动应用自己的程序”。流水线上按主人的装法复现（把打包好的应用放到按用户安装的位置，用它自带的命令行装隔离、跑自检）：第一次报“没有权限启动”（`CreateProcessAsUserW failed: 5`），第二次启动后直接崩。主人电脑上的表现是卡住不退，同一条路、同一个根子。这正是 11.1 里写着“待实测”的那一条。

**排除掉的另一个猜测**：家目录里被禁读的文件夹文件太多、加权限太慢。流水线上放了 8 万个文件，自检第一次 11 秒、第二次 4 秒，不是它。

**改法**：探针改成一份 PowerShell 脚本（`selfcheck-windows.ts` 的 `windowsProbeScript`），用系统自带的 PowerShell 跑，不依赖 Node，也不依赖应用自己的程序。每一项的做法和判定照原样搬过来；主人的家目录由外面算好传进去（隔离里的账户有它自己的家目录，不能在里面问系统）。

**验证**（流水线，三台机器结果一致）：

| 情况 | 结果 |
|---|---|
| 平常 | 通过，57 项；和原来 Node 探针在同一台机器上的结果逐项对比，56 项的结论和原因一字不差，另 1 项是当天新加的 |
| 程序目录放开给所有人 | 没过，只有“改派活工作台自己的程序”一项写得进 |
| 家目录里有真的 `.ssh`、`.claude`、`.codex`、`.cursor`（各两万个文件） | 通过 |
| 撤掉回环补丁 | 没过，正是那三项：浏览器调试口拿不准、本机监听端口连上了、在本机开监听口开成了 |
| **用打包后的应用自带的命令行，从按用户安装的位置** | 装隔离四步都好了，自检通过（9 秒，再跑 4 秒） |

真的派活时，在隔离里跑的是选手自己要跑的命令，不是平台的程序，所以这个毛病只在自检里。

## 12. 隔离自检不再拦派活，加固变成可选（2026-10-13 主人定）

**起因**：主人在自己的电脑上装了三轮，每一轮都卡在隔离上：要管理员确认、自检探针超时、最后是“外网”一项拿不准。主人的话是“都是我自己的电脑隔离什么”“你完全在把事情变大越来越复杂”。第 4 节那一整套依赖系统的账户、权限和防火墙，每台电脑情况不一样，一项不过整个应用就不能用，而且没有给人留出路。

**改成**：做减法。

- Windows 上自检不拦派活。装好就能用，不用管理员确认，不用装任何东西。
- 缺省用 Codex 自带的、不用安装的那种隔离（启动时明写，权限表不带禁读名单）。
- 第 4 节那一整套改叫“加固”，可选：桌面应用的设置 → 通用里点一下装并检查。装好并且自检通过的电脑上，派活才用它；没装、没通过，就用缺省的。通过过的，过期了会自动重检一次。
- macOS 上什么都不变。

**缺省这一种到底挡什么**（流水线三台机器实测，什么都没装的机器，见 `scripts/probe/codex-endpoint.mjs` 里“没装隔离”的三项）：

| | 结果 |
|---|---|
| 活做不做得完 | 做得完 |
| 写这件活自己的副本、任务临时目录 | 写得进 |
| 写家目录 | **写不进** |
| 连外网、连本机端口 | 连得上（不拦） |
| 读钥匙和登录文件 | 不禁（这种隔离做不了按名单禁读；带着禁读名单它直接拒绝运行） |
| 带密钥字样的环境变量 | 看不到（这一层和隔离做法无关，照旧） |

另外两种写法都不能用：什么隔离做法都不写，选手的命令根本跑不起来；免安装的做法带上禁读名单，Codex 拒绝运行。

**权限表里一条都不加**（2026-10-13 主人电脑上撞到、流水线上复现）：第一版给只读的活另外放开了任务临时目录，Codex 这种隔离拒绝运行命令（“cannot enforce split writable root sets directly; refusing to run unsandboxed”）：它只认“只读”和“只能改工作目录”这两档原样，不认再拼别的可写位置。改成什么都不加以后：只读的活命令跑得起来，副本、临时目录、家目录都写不进；能改文件的活和上表一样。流水线里“真的派一件活”的检查因此加了只读的一遍。

**代价**：没装加固的 Windows 电脑上，联网总开关关着也拦不住选手上网，选手读得到钥匙文件。保护程度相当于主人自己直接用 Codex 的“只能改工作目录”那一档。主人知道并接受。

**和第 4 节的关系**：第 4.3 节的底线对照表、4.4 的自检清单，现在说的是“装了加固以后”保证什么。没装时保证的只有上面这张表。

## 13. 平台不在后台启动 PowerShell（2026-10-13 主人定）

**起因**：主人的电脑上装着火绒。派活时它弹“程序隐藏执行 PowerShell”的提醒，倒计时到了默认“阻止”。平台第一版有三处在后台起系统自带的 PowerShell：

| 哪一处 | 什么时候 | 被拦了会怎样 |
|---|---|---|
| 防休眠 | 每件活一次，陪到活结束 | 防休眠没了 |
| 读进程列表（停选手、判断选手还在不在） | 每件活结束、停止、清理时 | 选手停不掉，或者把已经结束的当成还在跑 |
| 送进回收站 | 清理时 | 换下来的东西留在登记处的暂存目录里 |

第二处关系到“看管进程出错时必须先停选手”这条底线，不能指望用户每次都点“允许”。

**改成**：三处都直接调系统接口，不启动任何别的程序（`src/core/native-windows.ts`）。

| 哪一处 | 系统接口 | 说明 |
|---|---|---|
| 防休眠 | `SetThreadExecutionState` | 看管进程自己申请，不再起帮手。申请挂在调用它的线程上（看管进程的主线程），进程一没（哪怕是被直接结束）申请就没了 |
| 读进程列表 | `NtQuerySystemInformation` | 一次读出全部进程的进程号、父进程号、创建时间。不用逐个打开进程，所以别的账户的进程也读得到，不要管理员身份。一次两三毫秒（原来一次零点几秒到几秒）。按系统实际写出的长度解析，名单对不上就报错，不拿半份去判断 |
| 送进回收站 | `SHFileOperationW` | 和原来的做法底下是同一个系统功能。放到别的线程去做，不卡住桌面应用 |

认进程的规矩（第 5 节：处处核对创建时间，防进程号被重用）一个字没改，换的只是数据从哪来。另外加了一道：看管进程起选手之前先读一次进程列表，读不到就不起选手（停不了的选手不启动）。

**看管、推进和文件锁也核对出生时间**（2026-10-14 补）：任务看管进程、群和小队的推进进程、文件锁的持有者和回收者都在登记 `pid` 时一起保存 `pidSince`；派发进程的 `queuedBy` 配套保存 `queuedSince`。Windows 上直接从同一份系统进程表读取出生时间，读不到就报错，不把新记录降成只看进程号。父进程登记后台进程、后台进程自己接手时都更新这两个字段，群退出和任务续接时也成对清掉旧身份。

单进程判断统一在 `platform.ts` 的 `alive(pid, since)`：Windows 上号还在、出生时间也在和 `treeOf` 相同的容差内（前 2 秒、后 5 秒）才算在。失联判断、续接等待、停止前的检查（包括 5 秒后强制结束看管进程）、群与小队的推进和锁回收都用它。macOS 照旧只看号；升级前没有出生时间的记录也照旧按号认，不把仍在跑的旧任务判成失联。代价是老记录和容差内的极快重用仍保留原来的识别限制；这次不改进程树容差和原生系统接口。

**加了一个依赖**：`koffi`（让 Node 直接调系统接口的模块，开源，MIT 许可）。Node 24 自己没有这个功能。版本写死；它的安装脚本不运行（用的是它随包发的编译产物）。只在 Windows 上加载，macOS 的安装包不带它。

**安装包里怎么放**：这个模块不打进桌面应用的主程序，和 srt 一样放在应用的平台目录里（`resources/platform/node_modules`），主程序和命令行都从那里取。它找自己的编译产物时只看同一个文件夹里的邻居，所以两个包并排放（`scripts/prepare-platform.mjs`）；打包时核对两个包都在、版本一致、真正要加载的两个文件都在，缺了不出包；主程序里“运行时按位置加载模块”的写法只放行这一处（`scripts/check-desktop-bundle.mjs`）。平台的后台进程（每件活的看管进程、群和小队的推进进程）跑的是代码快照，快照不带 `node_modules`：由起它的一方用环境变量（`XAGENTS_KOFFI`）告诉它模块在哪，只在一处写（`node-runtime.ts` 的 `backgroundEnvironment`）。这个变量只有自己目录里没有模块的进程才听（命令行和桌面应用的主程序不听），也不往下传给选手。第一版漏了看管进程这一路，Windows 流水线的测试当场拦住。

**实测**：三台 Windows 机器，新旧做法逐项对照，带管理员身份和不带各一遍，再用装好的应用自己的程序跑一遍，全部一致。见 [research/windows-native-2026-10-13.md](research/windows-native-2026-10-13.md)。

**顺带露出来的一个老问题**（和换接口无关，换完才看得见）：派活进程在准备阶段被直接杀掉时，Windows 只带走它直接起的那一个进程，那一个自己起的子孙还在跑，还占着副本目录。这时 `xagents stop` 看到“最上面那个不在了”就不去收，`clean` 随后因为目录被占而失败。以前的测试没测到：测试里的准备命令在 Windows 上其实没跑起来（路径里没加引号的反斜杠被 Git 的 sh 吃掉），而读进程列表要一两秒，正好把这一点盖住。

改成：`stop` 和 `clean` 问“准备进程还在不在”时，Windows 上连它留下的子孙一起看，有就算还在，`stop` 会把它们收走。找“留下的子孙”有期限：只认出生在这件活结束之前的。没有这个期限的话，一件早就结束的活会把后来用过同一个进程号的无关进程的子进程认成“留下的”，`stop` 就会杀错。别处的“还在不在”判断不变（只认最上面那个，核对创建时间）。

**选手这一路也加了同一个期限**（同日补）：`stop` 里停选手进程树的几处原先没有期限。看管进程被直接杀掉或电脑重启后，活成了“失联”，主人过了很久才 `stop`，这时记录里的选手早就不在了，走的正是“找留下的子孙”那一支。现在 `stop` 里凡是按任务记录去找的（准备进程、选手），都带同一个期限，算法只写在一处（`job.ts` 的 `leftBy`）：

| 这件活 | 期限 | 为什么可靠 |
|---|---|---|
| 还没结束 | 现在 | 留下的不可能出生在将来 |
| 看管进程自己收尾的 | 记下的结束时间 + 5 秒 | 记结束时间之前，看管进程已经等到选手退出并收过一遍 |
| 失联的 | 记下的结束时间 + 5 秒 | 这个时间是平台发现“看管进程不在了”的那一刻；看管进程一没，系统就带走它直接起的选手，选手直接起的子进程只可能出生在这之前 |

期限宁可偏晚不能偏早（偏早会漏掉真留下的选手子进程，那是底线）。所以：

- 不用“选手最后一次有动静的时间”（记录里的 `lastActivityAt`）。那是选手最后一次有输出的时间，选手不出声时照样能起进程，拿它当期限会漏。
- 多留 5 秒：系统先让别人看到“看管进程没了”，再收走它起的选手，中间差一瞬；这一瞬里选手还能起进程。
- 没有给看管进程加“每隔几秒报一次平安”的记录。它只能说明“那一刻看管进程还活着”，说明不了“之后多久就没了”（休眠刚醒、写记录失败时都会偏早），要让它不偏早就得再加一条“报不了平安就停选手”，是新的出错路子，先不做。

顺带改的两处：`clean` 对失联的活问“选手还在不在”时，Windows 上也连留下的子孙一起看（同一个期限），有就让先 `stop`；叫醒群里、小队里的下一轮时，上一轮的选手进程号不带进新一轮（新一轮算“还没结束”，期限是现在，照着旧号去找等于没有期限）。

**这个期限管不到的**：失联一直没人发现。记下失联的是命令行的各条命令、别的活的看管进程、群和小队的推进进程，桌面应用的看板只显示、不改记录。电脑重启后要是头一条命令就是 `stop`（或在桌面应用里点停止），结束时间就是这一刻，期限等于现在，起不到作用；这时仍和以前一样，只靠“出生不早于起选手的时间、不晚于现在占着这个号的进程的出生时间”来挡。另外，`stop` 把一件早就结束的活改成“已停止”时会把结束时间记成停的这一刻，之后对同一件活再问，期限就跟着变晚。

**还会启动 PowerShell 的**只剩主人自己点的加固那一套（安装、自检里的探针，第 4、12 节），有测试守着：核心和桌面应用的后台代码里，别处出现 `powershell.exe` 测试就不过。

**没验的**：流水线的机器上只有系统自带的杀毒，没有火绒、360 这类。现在平台不再启动 PowerShell，那一种提醒不会再有；它们对“程序加载一个没有签名的模块”会不会另有提醒，要在主人的电脑上看。

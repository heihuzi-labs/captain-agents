# Windows 上 Codex 自带隔离的实测（2026-10-12）

给 [design-windows.md](../design-windows.md) 第 4 节当依据。探针是 `scripts/probe/windows-codex.mjs`，由流水线 `.github/workflows/windows-probe.yml` 在三台真的 Windows 机器上跑；想重测，把代码推到公开仓库名字以 `probe/` 开头的分支，结果在这次运行的附件里。

## 在哪测的

| 机器 | 系统 | Codex |
|---|---|---|
| GitHub 托管，`windows-2022` | Windows Server 2022（10.0.20348），x64 | codex-cli 0.162.1（官方安装脚本，固定版本） |
| GitHub 托管，`windows-2025` | Windows Server 2025（10.0.26100），x64 | 同上 |
| GitHub 托管，`windows-11-arm` | Windows 11 企业版（10.0.26200），arm64 | 同上 |

三台都是管理员账户、没有登录 Codex、Windows 防火墙三个配置文件都开着。**三台的结果逐项一致**，下面不再分开写。

没测的：真的让模型干活（要登录）；主人自己的电脑（普通账户、会弹管理员确认框、装了杀毒软件和代理软件的环境）。

## 怎么测的

1. 外面先准备：一个当“副本”的目录、一个当“任务临时目录”的目录、家目录里一个普通文件和一个“密钥”目录、盘符根下三个分别允许“所有人 / 已登录用户 / 本机用户组”修改的文件夹、凭据库里一个随机名的测试条目、几个本机监听口和一个命名管道、一个名字带 KEY 的假环境变量。
2. `codex sandbox setup --elevated --current-user` 装隔离。
3. 用 `codex -c windows.sandbox="elevated" sandbox -P <权限表> -C <副本> -c <权限表内容> -c <环境变量规则> -- node <探针>` 在隔离里跑探针。权限表 `xa` 和 macOS 上同一个思路：继承 `:workspace`（只读题继承 `:read-only`），“密钥”目录禁读，系统临时目录只读，任务临时目录可写；`TEMP`、`TMP` 指向任务临时目录。
4. 对照组：同一份探针在隔离外跑一遍（每一项都通，说明探针本身没问题）。

## 结论

**成立的**（可以写进启动参数）：

- 管理员装一次的那种隔离，命令确实换成专用的低权限账户来跑；允许联网时换成另一个专用账户。
- 只能写副本和任务临时目录；只读题连副本也写不进。
- 权限表里逐个路径禁读是生效的。
- 外网被拦；允许联网的开关生效。
- `shell_environment_policy.exclude` 生效：不带这条规则时，隔离里看得到主人的密钥变量；带了就看不到。和 macOS 上一样，这条必须带，外面那一层过滤也照做。
- 专用账户看不到主人凭据库里的条目，连不上隔离外进程开的命名管道。
- 只允许“已登录用户”或“本机用户组”修改的文件夹，隔离里写不进。

**不成立的**（和底线有出入，见设计文档 4.6）：

1. **本机端口没拦住。** 隔离里连得上本机任何监听口，也能自己开监听口。Codex 装了一条“拦本机回环 TCP”的防火墙规则（规则存在、已启用，方向是出站，远端地址是回环段，端口 1–65535），它自己的冒烟测试也期待直连本机被拦；但三台机器上实测都没拦住。Codex 另外装的 12 条系统过滤规则只管 ICMP、DNS 和文件共享端口，不管回环。这和“联网开关关着时不给选手开本机端口”这条底线直接冲突：本机常有代理软件、浏览器调试口在监听，连得上代理就等于能上外网。
2. **允许“所有人”修改的文件夹挡不住。** Codex 官方文档自己也这么写。
3. **家目录下的东西默认读得到**（应用数据目录、存凭据的系统文件夹都列得出）。所以和 macOS 一样只能靠名单逐个禁读，名单要按 Windows 的位置重写。存凭据的文件夹里的内容是按账户加密的，专用账户解不开，但名单上仍然要列。

**另外查到的**：

- **每个 Codex 文件夹要各装一次。** 换一个空的 `CODEX_HOME`（DeepSeek 就是这样用的），隔离直接报错（“Restricted read-only access requires the elevated Windows sandbox backend”）；对这个文件夹再跑一次安装命令就好了，先前那个文件夹不受影响。两个文件夹共用同一对专用账户。
- **不先装就用**：流水线的机器上不会弹窗，它会自己装（约 5 秒），但这第一次运行会失败（隔离里的进程看不了家目录下的 `AppData`）；明确装过之后再跑就正常。主人的电脑上这一步会弹管理员确认框，所以要先装、再派活。
- **明写另外两种隔离做法没有起作用**：装过以后，启动参数里写“免安装的那种”或什么都不写，实际跑的仍是专用账户。我们只认专用账户这一种，自检要核对隔离里的身份确实是它。
- **隔离里查不了“当前用户是谁”**：Node 的 `os.userInfo()` 在专用账户下报错。依赖它的工具可能出错，要在真的项目上再测。
- 隔离里 `USERPROFILE` 仍然指向主人的家目录，`TEMP`、`TMP` 按我们给的走。
- 装隔离不到 2 秒；每条命令进隔离多花 0.3–0.5 秒。

## 补救试验：自己给离线专用账户加“拦本机回环”的规则

脚本是 `scripts/probe/windows-loopback-fence.ps1`（系统自带的 PowerShell，要管理员权限，不带任何额外程序）。它往系统的过滤平台（WFP，Codex 那 12 条规则用的也是它）加 6 条只对 `CodexSandboxOffline` 这一个账户生效的持久规则：连出到本机回环的拦（IPv4、IPv6）、开监听口拦（IPv4、IPv6）、从本机回环收进来的拦（IPv4、IPv6）。

同一天在同样三台机器上测，三台结果一致：

| 项 | 装之前 | 装之后 | 装之后、允许联网 | 装之后、隔离外（主人账户） | 撤掉之后 |
|---|---|---|---|---|---|
| 连本机监听口（127.0.0.1、::1、本机局域网地址，Node 和 curl） | 通 | **挡** | 通 | 通 | 通 |
| 在本机回环上开监听口 | 通 | **挡** | 通 | 通 | 通 |
| 外网 | 挡 | 挡 | 通 | 通 | 挡 |
| 副本内写（只读题除外） | 通 | 通 | 通 | 通 | 通 |
| 家目录写、读“密钥”文件 | 挡 | 挡 | 挡 | 通 | 挡 |
| 隔离里跑 `node`、`git`、PowerShell | 行 | 行 | 行 | 行 | 行 |
| 隔离里跑 Python 的 asyncio | 行 | **不行** | 行 | 行 | 行 |

- 安装退出码 0，报告“装了 6 条”；紧接着再装一次，结果一样，不叠加；撤掉退出码 0，之后回到装之前的样子。
- 只影响这一个账户：允许联网时用的 `CodexSandboxOnline`、主人自己的账户都照旧（所以“总开关打开后本机端口也通”这条规矩不受影响）。
- **副作用**：Windows 上有些程序启动时要在本机回环上自己连自己（Python 的 asyncio 就是）。装了规则以后，这类程序在隔离里起不来，报权限错误。Node、git、PowerShell 不受影响。这和 macOS 上“本机端口不能用，需要端口的测试交给负责人跑”是同一条规矩，只是 Windows 上波及的程序多一些，要写进给选手的共同规则。

还没验的：主人的电脑上会不会被杀毒软件或公司策略拦；重启以后规则是否还在（规则是按“持久”装的，流水线的机器没法重启）；Codex 升级或重装隔离后专用账户的编号变了，规则会不会失效（会失效的话自检的本机端口探针会报出来，重装一次即可）。

## 补测：安装脚本、Codex 文件夹禁读、两件活之间

同一天追加的三组探针，Windows Server 2022 和 Windows 11 上结果一致。

**一次装齐的脚本**（`sandbox/windows/setup.ps1`，由没提权的进程用“以管理员身份运行”调起）：给两个新的 Codex 文件夹各装一次隔离、再装回环补丁，三步都成功，结果写进指定的文件；之后在其中一个新文件夹下跑探针，副本可写、家目录不可写、外网和本机端口都被挡。流水线的机器本来就是管理员，所以没有弹窗；主人电脑上会弹一次。

两个坑，都已经按结果改了：系统自带的 PowerShell 按本机代码页读没有 BOM 的脚本，脚本里有中文会被读坏、整个脚本解析失败，所以两个脚本只用 ASCII 字符；`powershell -File` 不会把逗号分开的参数拆成数组，所以几个 Codex 文件夹用 `|` 拼成一个参数传。

**Codex 自己的文件夹怎么禁读**：

| 权限表里怎么写 | 隔离还能跑吗 | 读登录文件 | 读会话记录 | 列这个文件夹 |
|---|---|---|---|---|
| 不禁 | 能 | 通 | 通 | 通 |
| 整个文件夹禁读 | 能 | 挡 | 挡 | 挡 |
| 整个禁读，帮手程序所在的两个子目录另写“可读” | 能 | 挡 | 挡 | 挡 |

整个禁读不会把隔离弄坏，所以和 macOS 一样整目录禁。另外看到：**上一次运行加的禁读会留在磁盘上**（之后一次运行即使权限表里不再禁这个文件夹，它仍然读不到）。多挡不放是安全的方向，但意味着“某次不禁”不能靠改权限表立刻生效。权限表里写了本机不存在的路径不报错。

**两件活之间**：隔离里的命令都用同一个专用账户，所以单独验了后一件活能不能碰前一件活的东西。

| 第二件活（另一个副本、另一个临时目录）去做 | 同一个 Codex 文件夹 | 另一个 Codex 文件夹 |
|---|---|---|
| 写自己的副本、自己的临时目录 | 通 | 通 |
| 写第一件活的副本 | **挡** | **挡** |
| 写第一件活的临时目录 | **挡** | **挡** |
| 读、列第一件活的副本 | 通 | 通 |

写不进去的原因：Codex 给每个工作目录单独发一个“通行证”编号，副本上的写权限是给这个编号的，进程只带自己那个目录的编号。读得到别的副本和 macOS 上一样（副本本来就不在禁读名单里）。

## 禁读名单里本机没有的路径：Codex 会把它建成文件夹

第一次用平台自己的自检在流水线上跑时，自检后家目录里多出了 `.claude`、`Documents\PowerShell`、`Documents\WindowsPowerShell` 三个空文件夹，都不是探针建的。原因在 Codex 的源码里写明了（`windows-sandbox-rs/src/deny_read_acl.rs`）：禁读名单里的路径不存在时，它先用 `create_dir_all` 把路径建成文件夹，再加禁读权限，目的是防止隔离里的命令自己建出这个路径再去读。

照搬 macOS 的名单，在没有 `.npmrc`、`.netrc`、`.git-credentials` 的电脑上就会建出这些名字的**文件夹**，npm、git 之后读它们会出错。所以 Windows 上改成：

- 权限表里只写本机真实存在的路径（`sandbox.ts` 的 `codexPermissions`）。代价：活跑着的时候才新出现的文件，这件活挡不住，下一件派活时才挡得住。macOS 上不存在的路径照写。
- 自检里读类的探针，“本机没有”和“被挡住”同等对待（没有可读的东西）。
- 写类的探针只试本机现有的文件和文件夹；目标本身不在时，试离它最近的现有上级文件夹，不去新建目标。探针不再建任何固定名字的东西。

## 平台自己的命令在流水线上真跑（2026-10-12）

流水线里新开一个空的登记处，依次运行 `xagents selfcheck`、`xagents windows-setup`、`xagents selfcheck`、`xagents windows-setup --remove`、`xagents selfcheck`。Windows Server 2022、2025 和 Windows 11 三台结果一致：

| 步骤 | 结果 |
|---|---|
| 没装就自检 | 没过：“还没装好 Windows 上的隔离。请主人运行 xagents windows-setup…” |
| `xagents windows-setup` | 四步都成功：给主人的 Codex 文件夹、DeepSeek 的、自检用的各装一次 Codex 的隔离，再装回环补丁 |
| 再自检 | **通过**，54 项全部符合要求；自检后家目录里没有多出任何东西 |
| 撤掉回环补丁再自检 | 没过，报的正是三项：浏览器调试口（拿不准，没人接）、本机监听端口（连上了）、在本机开监听端口（开成了），并提示重新运行 `xagents windows-setup` |

通过的那一次，54 项的结果（Windows 11）：

| 结果 | 探针 |
|---|---|
| 写得进（应当写得进） | 副本、任务临时目录（`TEMP`、`TMP` 正好指向它） |
| 没有权限 | 硬链接、家目录写、命名管道、Codex 的登录文件、DeepSeek 文件夹、存凭据的两个系统文件夹、各家全局配置 21 处、开机启动文件夹、PowerShell 配置文件夹两处、Codex 和 Cursor 的安装位置、主人的临时目录、Windows 的临时目录、公共目录、程序数据目录、盘符根目录、npm 日志目录 |
| 连接被拒 | 浏览器调试口、本机监听端口、在本机开监听端口、外网 |
| 是另一个账户 | 隔离里的身份 |
| 看不到 | 带密钥字样的环境变量、凭据库里的测试条目 |
| 本机没有 | SSH 文件夹、npm 登录、Grok 和 Cursor 的登录、终端配置文件 17 处、常见凭据文件 27 处 |

最后一行要注意：流水线的机器是空的，这些文件一个都没有，所以“读密钥”这一类在流水线上其实没有真的测到“有文件、被挡住”。这要等主人的电脑上（那里有真的 `.ssh`、`.npmrc`）跑自检才算数；探针脚本里专门建的那个“密钥”目录被挡住，只说明机制成立。
